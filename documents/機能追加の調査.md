# 機能追加の調査：シンタックスハイライト／入力補完／コード整形

- 調査日：2026-09-18
- 対象：JavaCode Selection Runner v1.0.3
- 目的：以下3点の実現方法と工数を整理する
  1. シンタックスハイライトを付けたい
  2. 入力時に候補を出したい（例：`System.` と打つと `out` が候補に出る）
  3. コードを整形する機能が欲しい

---

## 0. 前提の確認（調査で分かったこと）

### 0-1. 同梱しているのは JRE ではなく JDK 相当

`dist/jre_win` の中身を確認したところ、**コンパイラと解析系のモジュールが含まれている**。

| 項目 | 内容 |
|------|------|
| サイズ | 約 52MB |
| 実行ファイル | `java.exe` / **`javac.exe`** / `javaw.exe` / `jdb.exe` / **`jshell.exe`** / `keytool.exe` / `serialver.exe` |
| モジュール | `java.base` `java.compiler` `java.logging` `java.xml` `java.prefs` `jdk.internal.jvmstat` `jdk.attach` `jdk.internal.opt` `jdk.zipfs` **`jdk.compiler`** `jdk.internal.ed` `jdk.internal.le` `jdk.jdwp.agent` `jdk.jdi` **`jdk.jshell`** |

**これは重要な前提**で、`jdk.jshell` と `jdk.compiler` があるため、
外部の言語サーバーを導入しなくても、同梱JDKだけで補完・整形を実現できる余地がある。

### 0-2. VS Code の標準機能との関係

VS Code 本体には Java の TextMate 文法（シンタックスハイライト用）が同梱されている
（`microsoft/vscode` リポジトリの `extensions/java`）。
一方、**IntelliSense（補完）とフォーマットは標準では提供されず、拡張機能が必要**。

## 1. 要望①：シンタックスハイライト

### 1-1. 現状

- `.java` ファイルは **VS Code 標準の文法定義で既にハイライトされる**（拡張機能なしで動作する）。
- 本拡張は `contributes.languages` で言語ID `java` に `.java` と `.jsh` を関連付けているため、
  **`.jsh` ファイルも Java としてハイライトされる**。

> **確認したい点**：現状どの場面でハイライトが効いていないか。
> 「`.java` を開いても色が付かない」のであれば別の原因（言語モードの設定など）が考えられる。
> 「もっと細かく色分けしたい」という意味であれば 1-2 が該当する。

### 1-2. さらに進める場合（セマンティックハイライト）

TextMate 文法は字句ベースのため、変数とクラスの区別などができない。
これを型情報に基づいて色分けするのが「セマンティックハイライト」。

| 方式 | 内容 | 工数 | 備考 |
|------|------|------|------|
| A. Red Hat 拡張を利用 | 「Language Support for Java™ by Red Hat」がセマンティックハイライトを提供 | 小（推奨の案内のみ） | 別途JDKとプロジェクト設定が必要 |
| B. 自前実装 | JShell の `SourceCodeAnalysis.highlights(String snippet)` を使い、VS Code の `DocumentSemanticTokensProvider` に接続 | 中 | 同梱JDK（21）で完結。JShellスニペット単位の解析のため、クラス定義全体の解析には工夫が必要 |

## 2. 要望②：入力時の補完（`System.` → `out`）

### 2-1. 実現方式の比較

| 案 | 方式 | 品質 | 工数 | 同梱JDKで完結 |
|----|------|------|------|----------------|
| **A** | 「Language Support for Java™ by Red Hat」を推奨・依存にする | 高（Eclipse JDT 相当） | 小 | × |
| **B** | 同梱JDKの JShell 解析APIを使って自前実装 | 中〜高 | 中 | ○ |
| **C** | 固定の候補リスト（`System.out` など）を返す | 低 | 小 | ○ |

### 2-2. 案A：Red Hat 拡張を利用する

- Extension Pack for Java（Red Hat の Language Support ほか6拡張）を導入すれば、補完・整形・デバッグが揃う。
- **利点**：実装不要。品質が高い。
- **欠点**：
  - 別途 JDK が必要（本拡張の「JDK不要で使える」という利点が薄れる）。
  - プロジェクト（Maven/Gradle や classpath）を前提とする作りで、単発の `.java` ファイルでは機能が制限される。
  - 初回起動が重い。研修などで多数の端末に配る場合は負担になる。
- **本拡張の立ち位置**：Red Hat 拡張を入れる前提なら、本拡張の価値は「選択範囲だけを即実行できること」に絞られる。

### 2-3. 案B：JShell の解析APIを使って自前実装する（有力）

同梱している `jdk.jshell` には、**JShell 自身のTab補完を実現しているAPI**が公開されている。

| API | 用途 |
|-----|------|
| `SourceCodeAnalysis.completionSuggestions(String input, int cursor, int[] anchor)` | カーソル位置に対する補完候補を返す（本要望そのもの） |
| `SourceCodeAnalysis.documentation(String input, int cursor, boolean computeJavadoc)` | シグネチャ・Javadoc の取得（ホバー表示に利用可能） |
| `SourceCodeAnalysis.analyzeType(String code, int cursor)` | カーソル位置の式の型を推論 |
| `SourceCodeAnalysis.listQualifiedNames(String code, int cursor)` | 修飾名の候補（import の補助に利用可能） |
| `SourceCodeAnalysis.highlights(String snippet)` | ハイライト情報（要望①のB案で利用可能） |

**構成イメージ**

```text
VS Code 拡張（TypeScript）
  └─ CompletionItemProvider を登録（言語 java）
        └─ 補完ヘルパー（Java、同梱JDKで常駐実行）
              └─ jdk.jshell の SourceCodeAnalysis.completionSuggestions()
                    └─ 候補一覧を JSON で返す
```

- ヘルパーは標準入出力で JSON をやり取りする常駐プロセスにすると、毎回のJVM起動（数百ミリ秒）を避けられる。
- **利点**：同梱JDKだけで完結する。本拡張の「JDK不要」という性格を保てる。JShellのTab補完と同じ挙動になるため、実行時の挙動とも一致する。
- **欠点**：
  - JShell は「スニペット単位」の解析のため、ファイル全体のクラス定義に対する補完は工夫が必要。
  - 実装量が増える（ヘルパーのJavaコード、プロセス管理、TypeScript側のプロバイダ）。
- **工数の目安**：ヘルパー＋プロバイダの試作で 2〜3日、実運用の調整を含めて 1週間程度。

### 2-4. 案C：固定の候補リスト

`System.` の後に `out` `err` `in` を出す、といった決め打ちの実装。
研修で扱う範囲が限られているなら短期的には有効だが、拡張性は無い。

## 3. 要望③：コード整形

| 案 | 方式 | 品質 | 工数 | 追加サイズ |
|----|------|------|------|-----------|
| **A** | Red Hat 拡張（Eclipse formatter）を利用 | 高 | 小 | なし（別途JDK必要） |
| **B** | google-java-format を同梱して実行 | 高 | 中 | jar 数MB |
| **C** | 簡易整形（インデントのみ）をTypeScriptで実装 | 低 | 小 | なし |

### 3-1. 案B：google-java-format を同梱する（有力）

- 配布形式：`google-java-format-<version>-all-deps.jar`（依存込みの単一jar）
- 実行方法：`java -jar google-java-format-<version>-all-deps.jar <options> [files...]`
- **必要なJavaバージョン：21以上**（同梱JDKが21なので条件を満たす）
- JDK16以降では JDK 内部APIへのアクセス許可が必要で、以下6つの `--add-exports` を付けて起動する。

```text
--add-exports=jdk.compiler/com.sun.tools.javac.api=ALL-UNNAMED
--add-exports=jdk.compiler/com.sun.tools.javac.code=ALL-UNNAMED
--add-exports=jdk.compiler/com.sun.tools.javac.file=ALL-UNNAMED
--add-exports=jdk.compiler/com.sun.tools.javac.parser=ALL-UNNAMED
--add-exports=jdk.compiler/com.sun.tools.javac.util=ALL-UNNAMED
--add-exports=jdk.compiler/com.sun.tools.javac.tree=ALL-UNNAMED
```

- 同梱JDKには `jdk.compiler` が含まれているため、この方式が使える。
- VS Code 側は `DocumentFormattingEditProvider` を登録し、「ドキュメントのフォーマット」やファイル保存時の整形に接続する。
- **注意点**：
  - 整形スタイルは Google スタイル（インデント2スペース）が既定。社内の研修で使う規約と合うかの確認が必要（AOSPスタイルの指定も可能）。
  - ライセンスは Apache License 2.0。同梱する場合はライセンス表記が必要。

### 3-2. 案C：簡易整形

波括弧に応じたインデント付けのみをTypeScriptで実装する方式。
「とりあえず段付けを揃えたい」程度なら短期間で実現できるが、折り返しや空白の正規化はできない。

## 4. まとめと推奨

| 要望 | 推奨案 | 理由 |
|------|--------|------|
| ① シンタックスハイライト | **まず現状確認** | VS Code 標準で `.java` `.jsh` ともハイライトされるはず。不足点の具体例を確認したい |
| ② 入力補完 | **案B（JShell解析API）** | 同梱JDKで完結し、「JDK不要で使える」という本拡張の利点を保てる |
| ③ コード整形 | **案B（google-java-format 同梱）** | 同梱JDK21で動作。品質が高く、実装量も中程度 |

### 別の選択肢

「Red Hat の Extension Pack for Java を入れてもらう」方針であれば、②③は実装不要になる。
ただしその場合、利用者側で JDK の用意とプロジェクト設定が必要になり、
本拡張の「入れるだけで動く」という性格は失われる。
**どちらを重視するかによって方針が変わるため、先に方針を決めたい。**

## 5. 方針の決定と対応状況（2026-09-18）

運用担当者との確認により、以下のとおり決定した。

| 要望 | 決定 | 状況 |
|------|------|------|
| ① シンタックスハイライト | **要望から取り下げ**（VS Code 標準で既に効いているため） | 対応不要 |
| ② 入力補完 | **案B（同梱JDKの JShell 解析APIで自前実装）** | **対応済み（v1.2.0）** |
| ③ コード整形 | **案B（google-java-format 1.36.1 を同梱）** | **対応済み（v1.1.0）** |

- Red Hat の拡張機能は使わず、「入れるだけで動く」方針を維持する。
- 整形スタイルは Google Java Style で確定。
- VSIX への jar 追加（約3.8MB）は許容。

②の実装内容は [completion.md](completion.md)、③は [formatter.md](formatter.md) を参照。

### 残っている検討事項

- 整形スタイルを設定で切り替えられるようにするか（`--aosp` の指定）。
- 整形のたびに JVM を起動するため1秒前後かかる。補完ヘルパーは常駐しているため、整形を同じプロセスへ相乗りさせると改善できる。
- 補完ヘルパーを事前コンパイルして jar として同梱すれば、初回の待ち時間（数秒）を短縮できる。
- クラス定義の内部での補完精度を上げる工夫（カーソルを含むメソッド本体の抽出など）。

## 6. レビュー記録（2026-09-18）

実装後、使用している技術の公式ドキュメントと照合して確認・修正を行った。

### 6-1. 確認した公式ドキュメント

| 技術 | 確認先 | 確認した内容 |
|------|--------|--------------|
| VS Code 拡張API | `@types/vscode` の `index.d.ts`（`CompletionItem.range`） | 「range は単一行であり、補完要求が行われた位置を含む必要がある」 |
| VS Code 拡張API | Contribution Points（公式ドキュメント） | 「when 句はメニューに、enablement 句はコマンドに適用される。enablement は全メニューとキーバインドに効き、when は単一のメニューにのみ効く」 |
| VS Code / Java | Java in Visual Studio Code（公式ドキュメント） | IntelliSense と整形には拡張機能が必要。VS Code 本体は言語の基本サポート（文法定義）を同梱する |
| google-java-format | `UsageException` の使用方法メッセージ | `-` で標準入力→標準出力。`--offset` は0起点の文字位置、`--length` は文字数。両者は同数指定が必要で、指定時は対象を1つに限る |
| google-java-format | 公式README／jarのマニフェスト | Java 21以上が必要。JDK16以降は6つの `--add-exports` が必要（jarのマニフェストにも `Add-Exports` の記載あり） |
| JShell | `jdk.jshell.SourceCodeAnalysis`（Java 21 API仕様） | `completionSuggestions(String, int, int[])` で補完候補を取得できる |
| JShell | `jdk.jshell.execution.LocalExecutionControlProvider` | `name()` は `"local"` を返す。同一プロセス内で実行するプロバイダ |
| Java 起動ツール | `java` コマンド仕様（ソースファイルモード） | 先頭の非オプション項目が `.java` ならソースファイルモード。VMオプションはソースファイル名より前に置く。実行されるのは最初のトップレベルクラス。コンパイル結果はメモリ上に保持される |

### 6-2. 修正した内容

| # | 指摘 | 対応 |
|---|------|------|
| 1 | 補完の置き換え範囲が複数行にまたがる可能性があり、VS Code の仕様に違反する | 開始位置をカーソル行の先頭までに制限した |
| 2 | `CancellationToken` を受け取っておらず、取り消された要求も処理していた | 問い合わせの前後で取り消しを確認するようにした |
| 3 | 子プロセスの標準エラー出力を読んでいなかった（パイプが詰まって停止する恐れ） | 整形・補完とも受け取るようにした。補完は起動失敗時に1度だけ警告を表示する |
| 4 | 標準入力への書き込み失敗（相手の異常終了など）を捕捉していなかった | 捕捉して失敗として扱うようにした |
| 5 | ヘルパーの応答以外の出力（JVMの警告など）を応答と取り違える可能性があった | `OK` / `ERR` / `PONG` で始まる行だけを応答として扱うようにした |
| 6 | 整形で一時ファイルを作成・削除していた | 公式の使用方法に標準入力の指定（`-`）があることを確認し、標準入力方式へ変更した |
| 7 | 整形処理にタイムアウトが無かった | 30秒のタイムアウトを追加した |
| 8 | 大きなファイルで、入力のたびに全文を解析対象として送っていた | 最大20,000文字に制限し、切り出した分はアンカー位置を補正するようにした |
| 9 | 整形結果の改行コードが元のファイルと変わる可能性があった | ドキュメントの設定（`document.eol`）に合わせて変換するようにした |
| 10 | 入力が続いている状況で、古い補完要求も順番に処理していた | 送信前に最新の要求かを確認し、古いものは送らずに捨てるようにした |

### 6-3. 確認して問題が無かった点

- `--add-modules jdk.jshell` と `-Dfile.encoding=UTF-8` をソースファイル名より前に置いている（ソースファイルモードの要件を満たす）。
- 同梱JDKに `jdk.compiler` と `jdk.jshell` が含まれており、ソースファイルモードと JShell 解析APIの前提を満たす。
- `JShell.builder().executionEngine("local")` の指定子は正しい（実行用の別プロセスを起こさない）。
- `--offset` / `--length` を同数指定し、対象を `-`（標準入力）1つに限っている。
- `child_process.spawn` は引数を直接渡すため、パスの引用符付けは不要（ターミナルへ送る実行機能とは扱いが異なる）。

### 6-4. 未検証の事項

- **実機での動作確認は未実施**。この作業環境には Java が無いため、整形・補完とも実際の実行は試せていない。
  拡張機能を導入しての確認が必要。
- 特に確認したい点
  1. `System.` と入力して候補が出るか
  2. 初回の補完にかかる時間（ヘルパーの起動＋コンパイル）
  3. 常駐する Java プロセスのメモリ使用量
  4. 整形（`Shift+Alt+F` / `Ctrl+K Ctrl+F`）が期待どおり動作するか
  5. CRLF のファイルを整形しても改行コードが変わらないか

## 7. 当初の確認事項（回答済み）

1. **要望①について**：現在どの場面でハイライトが効いていないか。具体的な操作と画面を教えてほしい。
2. **利用者の環境**：Red Hat の拡張機能（および別途の JDK）を利用者に導入してもらえる前提か。
   研修用途で「入れるだけで動く」ことを優先するなら、自前実装（案B）が前提になる。
3. **整形スタイル**：Google スタイル（インデント2スペース）で問題ないか。
   社内の規約や研修テキストに合わせる必要があるか。
4. **配布サイズ**：現在 VSIX には約52MBのJDKが含まれている。
   整形用の jar（数MB）を追加することに問題はないか。
5. **優先順位**：3つの要望のうち、どれから着手するか。
